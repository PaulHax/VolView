### Verified failure mechanisms

- **Cached browser rejected by a remote availability probe.** The [original macOS job](https://github.com/Kitware/VolView/actions/runs/42528193208/job/128876359369) recorded five matching-browser lookup failures. A [controlled reproduction](https://github.com/PaulHax/VolView/blob/b4825f38f2415f31a17cfae37de32f129167c893/scripts/investigate-browser-setup.mjs) runs the installed WebdriverIO resolver with an existing cached Chrome and an injected HEAD-request connection reset: implicit setup rejects the browser; supplying its explicit binary succeeds without another HEAD request. This passed locally, on Linux, and on macOS ARM. The original failed HTTP response was not logged, so its specific transport cause is unknown. The installer downloads the pinned Chrome/ChromeDriver pair once per job, verifies both executable versions, and exports their paths.

- **Menu geometry can be stable while clicks are disabled.** The [original Linux job](https://github.com/Kitware/VolView/actions/runs/42528193208/job/128876359603) recorded intercepted “Show in all views” clicks. Vuetify disables pointer events during menu entry; WebdriverIO's stability check only compares geometry. The [browser control](https://github.com/PaulHax/VolView/blob/a0ea31fceff12fefb5e1b3f601106877bb18fe6b/tests/specs/menu-readiness-probe.e2e.ts) holds the real entry animation at a visible frame: the menu is stable, hit testing reports it unclickable, and the previous direct click fails with `element click intercepted`. The strengthened control starts `waitForClickable` while entry is still paused and verifies that it remains pending. Finishing entry releases the wait; the real command succeeds and the menu closes. The strengthened pending-wait variant is verified on Linux and, in the [fresh macOS control](https://github.com/PaulHax/VolView/actions/runs/42709442741/job/129474770496), on Apple Metal. That raw log records `pointerEvents: none`, the intercepted old click, then the wait remaining pending until entry finishes and the real command succeeds. An independent reviewer verified these results directly. The helper also scopes the item to its activator's menu. These results establish the blocked-click mechanism; they do not quantify how much it contributed to the historical 90-second timeout.

- **The repeated lifecycle case exhausted its test deadline while still making expected progress.** The [original Linux artifact](https://github.com/Kitware/VolView/actions/runs/42528193208/job/128876359603) contains the second cycle's restored-oblique image at about 81 seconds, then Mocha terminates the case at exactly 90.028 seconds before a final Four Up capture. Paired controls measured the remaining restored-oblique-to-Four-Up phase at 4.97–6.34 seconds on faster runners, while full lifecycle-spec time varied from 121.8 to 134.5 seconds. The intercepted menu clicks are independently real, but paired original/fixed helpers had nearly identical total times. A [first deadline control](https://github.com/PaulHax/VolView/actions/runs/42703394392) found that setting `this.timeout(120_000)` inside the test body was ineffective: the installed WebdriverIO 9.31.7 wrapper captured the old 90-second runnable timeout before invoking that body, and both the 90-second and intended 120-second cases stopped at 90 seconds after reaching the second restored-oblique state. The corrected [negative/positive control](https://github.com/PaulHax/VolView/actions/runs/42705113899) puts `.timeout(120_000)` on the test declaration, before WebdriverIO wraps it. The 90-second control again failed before Four Up; the 120-second case released an identical hold at 92 seconds, reached final Four Up at about 101 seconds, and passed all existing assertions. This proves the deadline repair, not the source of the historical runner slowdown. The shared 90-second limit remains unchanged.

- **View readiness precedes restoration of the selected tool.** The [later Linux failure](https://github.com/Kitware/VolView/actions/runs/42543112312/job/128922220468) could not find the second image's Data card after restore. A [regression reproduction](https://github.com/PaulHax/VolView/blob/b4825f38f2415f31a17cfae37de32f129167c893/src/components/__tests__/restorePanelReadiness.spec.ts) uses the real restore function and sidebar component, with segmentation deserialization held pending. Selecting Data after views bind is overridden when mask completion restores Paint and switches to Annotations. Waiting for restored Paint before selecting Data preserves the Data panel. The local negative control failed the intended Data-panel assertion; the corrected sequence passed. Both timing scenarios plus the existing view-restore checks passed on Linux and macOS ARM. The E2E test now waits for the saved Paint selection.
